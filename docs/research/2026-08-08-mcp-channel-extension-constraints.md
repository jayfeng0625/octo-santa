Research for GitHub issue #52. This document answers the research question only; it does not select or implement a protocol shape.

## Answer

MCP `2026-07-28` has no core primitive for an unsolicited, principal-aware application message with durable delivery, per-message acknowledgement, or replay cursor. It does have three useful seams:

1. A stateless, per-request capability envelope and `server/discover`, including negotiated extension maps.
2. A long-lived `subscriptions/listen` request, but its released core filter is closed to four change-notification selectors and has no replay position.
3. Vendor-prefixed custom methods and notifications, which the TypeScript SDK supports as application-owned protocol, subject to the transport having a live return path.

Claude Channels proves that a vendor can use the third seam over a persistent stdio process. It does not add delivery acknowledgement or replay: Claude Code explicitly drops unregistered/blocked events silently, and the server-side `await` confirms only a transport write. Claude's sender identity is metadata supplied after the channel server performs its own sender gate, not an MCP-authenticated principal.

Therefore a later prototype must keep message durability, principal authorization, delivery state, deduplication, acknowledgement, and replay position in the application protocol/storage. MCP can carry the live signal, but it does not provide those guarantees.

## Tasks extension status

Tasks must be treated as a separate draft extension, not as released `2026-07-28` core behavior.

### Confirmed in the extension draft

- Identifier: `io.modelcontextprotocol/tasks`; support is declared in each request's client extension capabilities and in server discovery ([draft lines 19-61](https://github.com/modelcontextprotocol/ext-tasks/blob/2c1425d9a288b9b1f489430fe1e00bb392b47e48/specification/draft/tasks.md#L19-L61)).
- Purpose: a server may turn a supported request, currently only `tools/call`, into a durable task handle. The client polls `tasks/get`; it can provide mid-flight input through `tasks/update` and signal cooperative cancellation with `tasks/cancel` ([draft lines 85-91](https://github.com/modelcontextprotocol/ext-tasks/blob/2c1425d9a288b9b1f489430fe1e00bb392b47e48/specification/draft/tasks.md#L85-L91), [poll/update/cancel lines 304-410](https://github.com/modelcontextprotocol/ext-tasks/blob/2c1425d9a288b9b1f489430fe1e00bb392b47e48/specification/draft/tasks.md#L304-L410)).
- Push is optional. Draft `taskIds` extends the listen filter and draft `notifications/tasks` carries a full task snapshot; polling remains permitted ([draft lines 412-507](https://github.com/modelcontextprotocol/ext-tasks/blob/2c1425d9a288b9b1f489430fe1e00bb392b47e48/specification/draft/tasks.md#L412-L507)). This is task-status observation, not a general channel-message log.
- Durable task IDs support reconnect polling only because the application/server persists task state. The extension explicitly tells clients to persist task IDs ([draft lines 304-310](https://github.com/modelcontextprotocol/ext-tasks/blob/2c1425d9a288b9b1f489430fe1e00bb392b47e48/specification/draft/tasks.md#L304-L310)). It does not define a stream replay cursor or delivery acknowledgement.

### Refuted or unverified for the pinned core/SDK

- The released `2026-07-28` core schema contains neither `taskIds` in `SubscriptionFilter` nor task request/notification types. Those additions exist only in the extension draft schema ([extension schema lines 314-374](https://github.com/modelcontextprotocol/ext-tasks/blob/2c1425d9a288b9b1f489430fe1e00bb392b47e48/schema/draft/schema.ts#L314-L374)).
- SDK v2 at the pinned commit explicitly does **not** implement the Tasks extension in its server conformance surface ([expected failures lines 35-50](https://github.com/modelcontextprotocol/typescript-sdk/blob/cc4b41617ce3601b1290d67216ea0b194a3cd9ac/test/conformance/expected-failures.yaml#L35-L50)). Its typed maps reject `tasks/*` and task notifications; explicit custom schemas are required for interop ([migration note lines 666-692](https://github.com/modelcontextprotocol/typescript-sdk/blob/cc4b41617ce3601b1290d67216ea0b194a3cd9ac/docs/migration/support-2026-07-28.md#L666-L692)).
- The extension draft still specifies missing-capability code `-32003` ([draft lines 63-82](https://github.com/modelcontextprotocol/ext-tasks/blob/2c1425d9a288b9b1f489430fe1e00bb392b47e48/specification/draft/tasks.md#L63-L82) and [lines 782-800](https://github.com/modelcontextprotocol/ext-tasks/blob/2c1425d9a288b9b1f489430fe1e00bb392b47e48/specification/draft/tasks.md#L782-L800)), while released core `2026-07-28` assigns Missing Required Client Capability to `-32021`. The extension draft is therefore not aligned with the released core error allocation at these exact commits. A prototype must not silently choose one.

Tasks can model a long-running operation initiated by a request. They do not solve unsolicited inbox delivery: there is no initiating request to augment, and task status is not a principal-scoped message envelope.

## Claude Channels vendor reference

### Confirmed behavior

- Claude Channels is a research-preview, stdio-only host extension. A server declares `capabilities.experimental['claude/channel'] = {}` and emits `notifications/claude/channel` with `{ content: string, meta?: Record<string, string> }` ([Anthropic Channels reference](https://code.claude.com/docs/en/channels-reference), “What you need,” “Server options,” and “Notification format,” accessed 2026-08-08).
- The capability uses the vendor `experimental` map, not MCP `2026-07-28` extension negotiation through `capabilities.extensions`. Official Telegram source confirms `experimental['claude/channel']` and optional `experimental['claude/channel/permission']` ([Telegram source lines 382-407](https://github.com/anthropics/claude-plugins-official/blob/ffbd6d5a9514c3e05363596161d98cb0f8798f5b/external_plugins/telegram/server.ts#L382-L407)).
- Inbound content is injected into the active model session as a `<channel>` event. `meta` entries become tag attributes; `source` is derived from the configured server name. Events only arrive while the Claude session is open ([Anthropic Channels guide](https://code.claude.com/docs/en/channels), introduction and quickstart, accessed 2026-08-08).
- Claude Code does not acknowledge channel notifications. The server's awaited notification call resolves after writing to the transport, not after Claude processes it. If the host did not register the server as a channel or policy blocks it, events are silently dropped ([Anthropic Channels reference](https://code.claude.com/docs/en/channels-reference), “Notification format,” accessed 2026-08-08).
- While Claude is busy, events queue in arrival order and are grouped into the next turn. The contract does not claim durable queuing across process/session failure ([same notification-format section](https://code.claude.com/docs/en/channels-reference)).
- Principal gating belongs to the channel server. Anthropic warns that an ungated channel is a prompt-injection path and requires checking the sender identity, not merely the room identity ([Anthropic Channels reference](https://code.claude.com/docs/en/channels-reference), “Gate inbound messages,” accessed 2026-08-08). Official Telegram code gates first, then supplies `user_id`, `chat_id`, and related routing fields as metadata before emitting the notification ([Telegram source lines 900-985](https://github.com/anthropics/claude-plugins-official/blob/ffbd6d5a9514c3e05363596161d98cb0f8798f5b/external_plugins/telegram/server.ts#L900-L985)). Metadata itself is not an authentication proof.
- The permission relay is another vendor notification pair with a short request ID and explicit allow/deny result. It is not a general channel-message acknowledgement. Official source registers `notifications/claude/channel/permission_request` only after declaring the permission capability ([Telegram source lines 411-440](https://github.com/anthropics/claude-plugins-official/blob/ffbd6d5a9514c3e05363596161d98cb0f8798f5b/external_plugins/telegram/server.ts#L411-L440)).
- Claude Code introduced `--channels` in version `2.1.80` as research preview and permission relay in `2.1.81` ([Claude Code changelog lines 2952-2988](https://github.com/anthropics/claude-code/blob/2bb60696142b493eafaeacfe00eac51d16c50c4f/CHANGELOG.md#L2952-L2988)). The public docs explicitly warn that flag syntax and protocol contract may change.

### What Claude does not establish

- It does not prove compatibility with MCP `2026-07-28`; the documented examples use the monolithic `@modelcontextprotocol/sdk` package and an `experimental` capability map, while the underlying MCP revision is not pinned.
- It does not negotiate a channel schema/version, acknowledge delivery/processing, expose a reconnect cursor, replay missed events, or persist events across a closed session.
- It does not make a server-supplied `user_id`, `source`, or other `meta` value trustworthy. Trust comes from the channel adapter's external authentication and allowlist before emission.
- It does not run over standard Streamable HTTP. Claude Code spawns the channel locally and uses stdio.

## Constraints for a later protocol prototype

These constraints follow from the evidence without selecting the extension design:

1. **Persistence is authoritative.** Store each application message before attempting push. Push can only wake or hint; polling/read must recover every message.
2. **Define principal scope in the application contract.** Bind each message/subscription/read/ack to an authenticated principal established outside self-reported MCP `clientInfo` or notification `meta`. Authorize reads as well as writes.
3. **Use explicit durable identifiers.** At minimum define message/event ID, destination principal or mailbox, stable ordering key, and application cursor/sequence. Do not reuse MCP pagination `Cursor` or the transient listen request ID as a delivery cursor.
4. **Make replay explicit.** On reconnect, open a fresh live path and separately request messages after the last durable application cursor. Expect overlap between replay and push; consumers must deduplicate by message/event ID.
5. **Make acknowledgement an application request.** A JSON-RPC notification cannot be acknowledged. Define a request/tool/custom method if acknowledgement is required, and specify whether it means transport receipt, wrapper receipt, model presentation, processing completion, or business acceptance.
6. **Negotiate the exact extension version and fallback.** For native MCP `2026-07-28`, use a prefix-qualified entry in `capabilities.extensions` with a settings/version object. Do not infer support from a custom notification arriving. Define behavior when either side omits the extension.
7. **Keep core listen limitations visible.** The released SDK listen router only understands four core change events. Adding an application message selector requires extension-specific client and server schemas/router behavior, or a separate custom long-lived request. Merely adding a field to JSON will not make SDK v2 deliver it.
8. **Separate transport adapters.** A Claude adapter can emit its research-preview `experimental['claude/channel']` notification over stdio as best-effort delivery. A standard MCP `2026-07-28` adapter must use its independently negotiated extension contract. Do not call Claude's shape standard MCP.
9. **Treat HTTP and stdio differently.** Stdio provides a process-lifetime bidirectional path for vendor notifications. Modern Streamable HTTP has per-request response streams and no independent GET stream, so unsolicited extension delivery needs `subscriptions/listen` integration or another explicitly negotiated long-lived request.
10. **Specify ordering and backpressure.** MCP promises neither durable ordering across reconnect nor an overflow policy. Define queue bounds, batching, duplicate handling, slow-consumer behavior, and what happens when the live writer fails.
11. **Keep Tasks orthogonal.** A future Tasks adapter may represent work initiated by a request, but must not become the inbox protocol. At the pinned versions it is draft-only, error-code-inconsistent with core, and unsupported by SDK v2's typed server runtime.
12. **Treat cancellation as connection/work intent only.** Cancelling a listen tears down live delivery; it must not acknowledge, delete, or advance durable message state. Task cancellation is also cooperative and eventually consistent.
13. **Define observable failures.** Establish request errors for unsupported capability, invalid principal/cursor, expired cursor, and storage failure. Since pushes cannot return errors, expose health/lag and failed-attempt state through a request/read surface or operational telemetry.
14. **Verify cross-process behavior.** SDK v2's default `ServerEventBus` is in-memory and explicitly requires a consumer-supplied pub/sub implementation for multi-process deployments ([SDK event bus lines 21-45](https://github.com/modelcontextprotocol/typescript-sdk/blob/cc4b41617ce3601b1290d67216ea0b194a3cd9ac/packages/server/src/server/serverEventBus.ts#L21-L45)). Octo-santa's SQLite boundary must source each process's local writer independently.

## Gaps and conflicts to resolve experimentally

1. **SDK custom listen extensibility:** SDK v2 supports custom methods/notifications, but its built-in `subscriptions/listen` schema and event bus are closed to four core change types. Verify whether a clean consumer extension hook exists by the prototype date; none is present at the pinned commit.
2. **Tasks revision alignment:** Obtain a tagged Tasks extension release aligned to core `2026-07-28`, including the corrected missing-capability error code, before relying on any task notification schema. The pinned repository is draft-only and contradictory.
3. **Host support matrix:** Test target clients, not just schema acceptance. Extension capability advertisement does not imply a host exposes custom unsolicited notifications to the model or UI.
4. **Claude lifecycle behavior:** Public docs define active-session ordering and silent drops but not queue bounds, restart behavior, duplicate behavior after MCP reconnect, or whether queued events survive compaction/navigation. Treat all as unverified until driven against the exact Claude Code build.
5. **Claude protocol version:** Anthropic's public channel docs do not pin the underlying MCP protocol revision or an extension version. The documented `experimental` capability shape and SDK imports indicate a legacy host extension, but exact wire-version negotiation remains unverified from public Claude Code source.
6. **Principal propagation:** Standard HTTP authorization authenticates the request, but neither core listen notifications nor Claude channel metadata define a cryptographically bound principal envelope. Prototype the authorization boundary end to end, including replay reads, live fan-out, acknowledgements, and reconnects.
7. **Delivery semantics vocabulary:** Decide and name distinct states before prototyping: persisted, selected for principal, attempted, written to transport, presented to wrapper/model, processed, and business-acknowledged. Neither MCP subscription acknowledgement nor Claude's awaited notification collapses these safely.

## Disposition of named mechanisms

| Named mechanism from issue #52 | Disposition |
| --- | --- |
| `subscriptions/listen` | Adopt as verified transport affordance, but only for its released four-filter core shape unless an extension adds and implements more. |
| Extension capabilities | Adopt for `2026-07-28` negotiation; version the extension settings and define fallback. |
| Notifications | Adopt only as best-effort one-way signals; never as implicit acknowledgement. |
| Resources | Park as an invalidation/read option, not a message envelope. |
| Tasks | Park for channel delivery. Revisit only for long-running request execution after a compatible released extension/SDK exists. |
| Stateless connections | Adopt as a design constraint: no principal, conversation, cursor, or capability state may be inferred from connection identity/history. |
| Cancellation | Adopt only for stopping in-flight work/listen streams; it has no durable message-state meaning. |
| Errors | Adopt JSON-RPC request errors and the released `-32021` capability code; define application errors outside MCP's reserved range. |
| Reconnect cursor | Refuted as built-in; define an application cursor and replay request. |
| Acknowledgements | Refuted as per-message built-in; define an application request with precise semantics if needed. |
| Observations | Refuted as a released named MCP mechanism; no official schema found. |
| Claude channel extension | Adopt only as a vendor adapter/reference: research preview, stdio, experimental capability, silent-drop/best-effort delivery. |
