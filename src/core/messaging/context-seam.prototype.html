PROTOTYPE / throwaway

Where should Messaging end and the Delivery Gateway begin?

Question: Which ownership and interface shape gives Envelopes, Deliveries, sender authority, repository isolation, and delivery evidence a coherent home without making Legacy Messaging’s Agent, Channel, and Message model a permanent constraint?

Disposable decision aid. This is not production code, a migration plan, or a preselection of a winner.

Verified starting point

The comparison starts from today’s runtime, but Legacy Messaging behavior is removable and is not a compatibility requirement for the future domain.

Legacy Messaging only

Agent, Channel, Message, membership, and read cursor. MessagingService depends on AgentRepository, ChannelRepository, and MessageRepository.

Identity is not authority

An Agent name is caller-selected and then bound to PID/stdio registration. Channels are global and open to registered agents; DMs use sorted Agent IDs.

Durability and notification

SQLite is the cross-process bridge. Durable cursor reads are authoritative; notification push is separate and best-effort.

Gateway concepts are new

No repository scope, idempotency, correlation/reply identity, Envelope, Delivery, Submission, or Observation exists in the current domain.

Wrapper-mediated I/O

The model emits structured intent. Deterministic wrappers own protocol mechanics, sender attestation, route resolution, retries, and timeouts.

Canonical distinction

Envelope is admitted sender-neutral content and intent. Delivery is per destination. Submission proves harness acceptance; Observation is later, separate visibility evidence.

Three architecture shapes

Switching shape resets the in-memory run. The same actions produce equivalent externally required semantics, while the owner and crossing trace changes.

Drive the model

Every action goes through authenticated wrapper intent, deterministic admission and routing, then updates the complete readable state. SQLite remains the durable cross-process bridge in every shape.
